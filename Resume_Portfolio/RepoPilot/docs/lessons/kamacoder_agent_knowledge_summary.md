## 1. Agent 的最小定义：从“生成回答”到“围绕目标行动”

普通聊天模型的主要产物是文本回答：用户提问，模型基于现有上下文生成回复。它可以给建议，但不会
天然访问环境、验证建议或根据外部结果自行调整。

Agent 则是一个**有目标、有状态、可行动、会反馈迭代**的系统。一个实用的最小式是：

```text
Agent = Model + Context + State + Tools + Control Loop + Runtime Boundary
```

其中模型负责理解和提出下一步；但真正决定可靠性的，通常是模型外的系统部分：工具定义与执行器、
上下文装配、状态持久化、权限、预算、验证、审计和恢复机制。

### 1.1 四项核心能力

| 能力 | 含义 | 失败时的典型表现 |
| --- | --- | --- |
| 规划 | 把目标拆为可验证的子问题，并保留完成标准 | 只列计划不执行；做两步就提前下结论 |
| 工具 | 通过受限接口读取或改变外部环境 | 工具名含糊、参数乱填、错误地把“建议”当“执行” |
| 执行 | 推进每一步并处理分支、失败与依赖 | 工具失败后假装成功；无法恢复中断任务 |
| 反馈 | 把 Observation 转为下一步决策，而非机械顺序调用 | 重复调用同一工具；忽略工具的失败或证据 |

判断一个系统是否具有 Agent 特征，关键不在“是否用了 LLM”或“是否调用了函数”，而在于：它是否会在
完成任务的过程中，依据任务状态和观察结果决定下一步。若调用路径完全由代码预先写死，它更接近带
模型能力的 Workflow。

### 1.2 Agent、Chatbot、RAG、Workflow 的边界

| 形态 | 控制权 | 适用问题 | 主要优势 | 主要风险 |
| --- | --- | --- | --- | --- |
| Chatbot | 用户一问一答 | 解释、写作、建议 | 简单、低延迟 | 无法验证或操作外部环境 |
| RAG 问答 | 固定检索—生成路径 | 有清晰资料库的问答 | 可引入外部知识 | 检索差、上下文噪音、仍不一定会行动 |
| Workflow | 代码和规则控制路径 | 步骤稳定、规则可预先列全的任务 | 可预测、可审计、成本低 | 对开放问题适应性弱 |
| Agent | 模型在约束下控制开放节点 | 路径未知、需多工具探索的问题 | 能基于证据调整策略 | 成本、延迟、可解释性和安全风险更高 |

关键原则是：**分支存在不等于必须使用 Agent**。只有当路径无法提前穷举，且需要依据中间观察作语义
判断时，才值得引入模型驱动的决策。常见的稳健架构是“外层 Workflow 管边界、权限和状态流转；内层
Agent 解决开放子问题”。

## 2. Agent 的基本运行循环与设计模式

### 2.1 ReAct：思考、行动、观察

ReAct 将 Reasoning、Acting 与 Observation 串成循环：模型根据目标和已有证据选择动作；运行时执行
受控工具；将结果作为 Observation 返回模型；模型再决定继续、转向、追问或交付。

```text
Goal + selected context
        ↓
Model proposes action / final answer
        ↓
Policy, schema and permission gate
        ↓
Tool execution → observation / structured error
        ↓
State update and next-turn context assembly
        └─────────────────────────────────────↺
```

ReAct 是很好的**推理—行动提示范式**，但不是完整的生产架构。裸循环常把所有历史和中间状态拼成文本，
容易发生上下文膨胀、重复调用、提前结束和不可恢复中断。

### 2.2 三种常见模式的选型

| 模式 | 工作方式 | 适合 | 不适合 / 风险 |
| --- | --- | --- | --- |
| ReAct | 边观察边选择下一步 | 工具探索、信息不完整的排查 | 容易绕路或陷入重复尝试 |
| Plan-and-Execute | 先形成计划，再逐步执行，并在检查点重规划 | 目标复杂、依赖关系明显的任务 | 计划过度僵化，或计划文本取代真实执行 |
| Reflection / Reviewer | 产出后由同一或独立组件检查，再修订 | 代码、报告、结构化答案等质量要求高的任务 | 反复自评会耗时耗费；不能替代外部验证 |
| Multi-Agent | 主 Agent 分派独立子任务，收集、核验和汇总 | 可并行且边界清楚的子任务 | 通信、汇总、冲突处理和成本显著增加 |

实务上应先用最小可控方案。单 Agent + 专用工具即可解决的问题，不应仅为了“看起来更智能”而拆成多
Agent。多 Agent 的价值来自**上下文隔离、独立规划与可并行性**，而不是数量本身。

### 2.3 计划不是证据，结束也不等于成功

模型形成的计划只是一种可调整假设。运行时应记录每个子目标、已确认事实、失败步骤、被否定的假设和
剩余缺口。最终交付前要由外部规则或验证器确认：

- 原始目标是否真的满足；
- 结论是否有可追溯的证据；
- 未验证的猜测是否被明确标注；
- 必要测试、检查或用户确认是否完成；
- 预算耗尽时是否诚实地交付阶段性结果而非编造结论。

## 3. 从 ReAct 到 Loop Engineering：治理五类循环变量

Loop Engineering 的关注点不是“如何写一个 `while`”，而是如何让持续运行的 Agent 收敛。每一轮真正
变化的是下列五类变量：

| 治理对象 | 必须回答的问题 | 常用机制 |
| --- | --- | --- |
| Context（上下文） | 本轮模型真正需要看什么？哪些内容应删除、压缩或按需取回？ | 选择、摘要、截断、JIT retrieval、工具输出上限 |
| State（状态） | 当前做到哪一步？事实、假设、失败和待办分别是什么？ | 显式 schema、checkpoint、状态差异、版本化 |
| Budget（预算） | 还允许消耗多少步、时间、Token、费用和并发？ | 每轮记账、硬上限、降级、优雅收敛 |
| Tools（工具集） | 这个阶段哪些能力应暴露？操作是否安全和可恢复？ | 候选工具裁剪、Schema、策略门、幂等性 |
| Termination（终止） | 什么情况下交付、追问、暂停、转人工或停止？ | 成功验证、缺输入、重复失败、超时、风险审批 |

### 3.1 独立状态优于“把 transcript 当数据库”

对话文本适合模型推理，不适合承担可靠数据库的职责。它会被压缩、截断、稀释，且难以跨进程恢复。
多步 Agent 至少应有结构化 Session State，例如：

```yaml
goal: "定位测试失败原因"
completed_steps: ["收集测试输出", "定位失败用例"]
confirmed_facts: ["测试命令退出码为 1"]
hypotheses: ["依赖版本冲突，待验证"]
rejected_hypotheses: []
failed_steps: []
missing_information: []
next_actions: ["读取锁文件", "复跑最小失败用例"]
budget:
  steps_left: 8
  deadline: "..."
```

模型每轮只需要看到与当前节点有关的状态投影；运行时保留完整状态、检查点与历史证据。这样即使上下文
重置，也能由持久状态恢复，而不是依赖模型“记得”。

### 3.2 防止循环失控的最小护栏

- **步数、Token、时间和工具调用上限**：任一预算触顶都需停止扩张，改为总结已知事实与缺口。
- **重复检测**：相同工具与等价关键参数重复失败时，不可无限重试。
- **结构化恢复**：缺参数→追问；超时→有限重试或降级；无权限→停止说明；无数据→调整范围或报告缺口。
- **显式完成门**：模型声称“完成”不是唯一终止条件；代码或验证器检查必需产物和关键证据。
- **取消与恢复**：用户中断、进程异常或审批等待后，保存可恢复的 checkpoint，而不是留下不明状态。

## 4. 工具工程：把 API 变成 Agent 可安全使用的能力

工具不是后端 API 的原样清单，而是模型可理解、可选择、可审计、可恢复的**行动边界**。一个工具契约应
清楚表达：

1. 能做什么、何时优先使用；
2. 不能做什么、不能替代什么；
3. 所需参数、格式、范围与默认上限；
4. 成功、失败、证据和建议下一步的结构化返回；
5. 权限、风险等级、幂等性与审计要求。

### 4.1 工具描述、参数与返回值

| 部分 | 推荐做法 | 要避免的做法 |
| --- | --- | --- |
| 名称与描述 | 使用具体动词和对象；写明适用与不适用场景 | `queryData`、`doAction`、`handle_problem` 等模糊名称 |
| 参数 Schema | 强类型、必填字段、`enum`、明确时间/数量/路径范围和上限 | 把整段自然语言塞入单一 `query` 参数，让工具再次猜意图 |
| 成功返回 | `success`、状态字段、证据/来源、时间范围、可选的下一步提示 | 仅返回一段自然语言，迫使模型重新解释事实 |
| 失败返回 | `error_code`、`recoverable`、`missing_fields`、`retry_after`、`recommended_action` | 只有“系统异常”，让模型猜该不该重试 |

“缺少关键参数”不是一次工具失败，而是需要向用户澄清的状态。系统应拒绝由模型猜测必填参数。

### 4.2 合理的工具粒度

工具过细会让模型承担过多机械编排，导致调用链长而脆弱；工具过粗又会隐藏过程、降低可解释性和故障
定位能力。较好边界是：**一个清晰业务动作 + 可判断的结构化输出**。

例如，阅读仓库、检索符号、运行测试、生成补丁、应用补丁、查看 diff 和验证修改可以是不同能力；但不
应将“解决所有代码问题”包装成黑盒超级工具，也不必将一次有明确上下文的代码查询拆为十个底层数据库
式调用。

### 4.3 读写分离与副作用控制

工具至少分为：

- **只读类**：读取文件、搜索、查询日志、运行不改变环境的检查；
- **草稿/计划类**：形成补丁、邮件、配置变更或执行计划，但尚未提交；
- **副作用类**：写文件、执行命令、删除、提交、发布、对外通信。

对于高风险副作用，推荐“计划/草稿 → 显示影响 → 用户确认 → 执行 → 审计”的状态机，而不是让模型
直接把“建议”跳成“已执行”。

## 5. Function Calling、MCP、Skills 与 A2A：四层不要混淆

| 概念 | 所在层 | 解决的问题 | 对 Agent 的含义 |
| --- | --- | --- | --- |
| Function Calling / Tool Use | 模型调用层 | 模型本轮选择哪个函数及参数 | 是“怎样表达一次工具请求” |
| MCP | 应用与能力接入层 | 如何发现、连接和调用外部工具、资源与提示模板 | 是“能力从哪里来、怎样标准化接入” |
| Skill | 方法与知识层 | 在特定任务上采用何种流程、约束和输出结构 | 是“应该怎样做得更稳” |
| A2A / Agent-to-Agent | Agent 协作层 | 独立 Agent 怎样描述任务、回传结果和管理生命周期 | 是“多个能自主规划的实体怎样协作” |

### 5.1 Function Calling 的完整宿主循环

模型只产生结构化调用意图；宿主程序才是实际执行者。因此完整流程应是：

```text
注册工具 schema → 模型返回 tool call → 参数/schema 校验
→ 权限与策略检查 → 执行或请求确认 → 记录 Observation
→ 将结果放回上下文 → 模型继续判断
```

模型不应绕过运行时直接触碰文件、Shell 或远程服务。并行调用只适用于确实相互独立的只读任务；如果
两个动作有写入冲突、数据依赖或同一预算约束，则并行会放大不确定性。

### 5.2 MCP 的定位

MCP 不是模型、Agent 框架，也不是 Function Calling 的替代品。来源将其概括为 Host–Client–Server
架构：Host 负责用户交互、上下文与权限决策；Client 与一个或多个 Server 协商能力；Server 暴露能力。

可用一句话区分：**Function Calling 决定模型如何请求一次能力；MCP 规范 AI 应用如何发现和接入能力。**
Host 可以把 MCP Server 的工具转换为模型侧可调用的 schema。

MCP 能力通常可按语义分为：

- **Tools**：Agent 主动执行的动作；
- **Resources**：可读的上下文数据，如代码、文档、schema；
- **Prompts**：可复用的任务模板和操作套路。

本地能力与远程能力的选型要同时考虑数据位置、身份验证、授权、网络边界、审计和使用者范围。MCP 的
标准化不能替代工具 Schema、最小权限或高风险审批。

### 5.3 Skills：把可复用过程从全局 Prompt 中拆出来

Skill 适合承载场景化工作法：触发条件、身份与目标、允许工具、步骤、禁止事项、输出 schema、验收标准。
它的价值在于按需加载，避免把所有领域规则塞入系统提示词造成上下文污染。

可用下式记忆：

```text
Skill 决定“按什么方法做”
MCP 决定“可以接入哪些能力”
Function Calling 决定“本轮怎样请求能力”
```

## 6. Context、记忆与 RAG：相互协作，但不是同一个东西

### 6.1 四层信息结构

| 层级 | 生命周期 | 保存内容 | 核心治理问题 |
| --- | --- | --- | --- |
| 短期上下文 | 当前调用 / 当前会话 | 最近对话、工具 Observation、即时规则 | 选择、压缩、排序与窗口上限 |
| Session State | 当前任务 | 目标、步骤、事实、假设、失败、待办、预算 | 结构化、可恢复、可验证 |
| 长期记忆 | 跨会话 | 稳定偏好、已确认项目背景、可复用结论 | 写入筛选、冲突、时效、删除和隐私 |
| 外部知识库 / RAG | 独立资料源 | 文档、代码、手册、规范、历史资料 | 检索质量、证据、更新与权限 |

RAG 是“按需获取外部知识”的机制，不自动等于长期记忆。向量数据库只是存储/检索手段；把原始聊天记录
全部塞进向量库只是“历史检索”，并不自动构成经过治理的记忆系统。

### 6.2 长期记忆的写入—读取—遗忘闭环

写入前需要判断：信息是否稳定、后续是否有用、是否被明确确认、是否涉及隐私或敏感数据。条目应带有
类型、来源、置信度、更新时间、适用范围及删除方式。

读取时应按当前任务检索、过滤过期/低置信度条目，只把关键内容放入本轮 Context。随后更新冲突项、
降低被推翻结论的权重、清除低价值或过期信息，并支持用户删除。记忆越多不一定越智能；无治理的记忆
会变成噪音和错误先验。

### 6.3 上下文污染的防治

对进入 Context 的信息至少标记为三类：

- **事实**：有来源、可回溯的工具结果、测试输出或文档证据；
- **假设**：用户猜测、模型推断、待验证原因；
- **废弃信息**：已经证伪、过期或确认无关的内容。

最终结论必须主要依赖事实；假设只能指引下一步验证；废弃信息不应继续参与推理。这个简单分类能降低
长任务中“某个早期猜测逐轮被当作事实”的漂移风险。

### 6.4 Coding Agent 的代码检索启示

代码库不应默认把所有内容向量化后检索。对于精确符号、文件名、调用位置和最近修改，文件树、Glob、
Grep、语义/AST 符号查询与按需 Read 通常更可解释、更容易验证。RAG 更适合作为补充：面向大量文档、
跨仓库知识或语义相关但关键词不稳定的资料。无论使用哪种检索，都应把命中的证据、范围和时间记录进
Trace，以便复盘“为什么看到这些内容”。

## 7. 从单 Loop 到 Graph、Multi-Agent 与 Harness

### 7.1 Graph Engineering：显式编排复杂任务

当任务出现并行分工、不同失败路径、校验、审批或断点恢复时，可把单一 Loop 外化为可执行图。图由
节点、边和状态构成：

- **节点**应尽量“单一且无聊”：职责清楚，才能单测、缓存、重试、替换；节点可以是规则函数，也可以
  是内部带 Loop 的 Agent；
- **边**是下一步决策。权限、测试结果和阈值等确定性决策应由代码控制；只有需语义判断且候选有限的
  路由才交给模型；
- **状态**应有 schema、版本和 checkpoint。模型看到的是状态投影，状态本身不是 transcript。

图不会取代 Loop：Loop 可以视为最简单的有环图；Graph 解决多个 Loop、工具和人工节点的编排，Loop
解决每个 Agent 节点内部的控制与收敛。

对每条模型路由边，至少记录输入状态、候选项、选择理由/置信度、后果与 fallback。对跨越“外部写入”
的边，在结构上设置权限、审批与预算门，而非事后补救。

### 7.2 多 Agent：独立协作者，而非更多 Tool

Tool 是一次被动调用；子 Agent 拿到任务包后可在独立上下文内规划、调用工具、调整策略并回传结果。
一个合格任务包应包含：目标、必要上下文、允许工具、输出 schema、截止时间/预算和风险边界。

主 Agent 汇总时不能简单拼接，而要处理：结果冲突、格式归一、低置信度过滤、证据校验和部分失败。典型
编排包括顺序管道、Map-Reduce、层级委派和路由分发。

适合多 Agent 的情形：任务可独立拆分、子任务可并行、子任务会产生大量中间上下文、不同角色/权限确实
不同。否则单 Agent + 专用工具通常更低成本、更易调试。常见中间形态是 **Agent-as-Tool**：主 Agent
把范围有限、权限更窄的子 Agent 作为一个能力调用，自己保留验收与最终控制权。

### 7.3 Harness Engineering：运行系统的“缰绳”

Harness 指把模型能力变成可控行动系统的整套运行外壳。可按六层理解：

| 组 | 层 | 要解决的问题 |
| --- | --- | --- |
| 输入侧 | Context 精细化 | 本轮模型应看到何种目标、规则、证据和工具说明 |
| 输入侧 | 记忆与状态 | 跨轮、跨重启应保留什么，如何恢复 |
| 动作侧 | 工具系统 | 可以做什么、如何校验、如何限制权限 |
| 动作侧 | 执行编排 | 如何规划、路由、并行、重试和停止 |
| 校验侧 | 评估与观测 | 如何知道结果和轨迹是否可靠 |
| 校验侧 | 约束与恢复 | 不能做什么，失败后如何安全地继续或停止 |

Prompt Engineering 关注“怎样表达指令”，Context Engineering 关注“给模型什么信息”，Harness Engineering
则覆盖“如何让整个长链路运行系统持续做对事”。三者是包含关系，不是互相替代的潮流名词。

## 8. 安全、权限与恢复：模型负责提案，系统负责守门

Agent 的自由度越高，越需要把安全规则置于模型之外。典型故障与相应控制如下：

| 故障模式 | 根因 | 运行时护栏 |
| --- | --- | --- |
| 死循环 | 缺少预算、失败记忆和完成判断 | 步数/时间/Token 上限；等价调用去重；停止条件 |
| 误调用 | 工具描述、粒度或参数不清晰 | 工具候选裁剪、严格 schema、预执行规则校验 |
| 多步中断 | 任务进度只存于聊天文本 | 显式 Session State、checkpoint、可恢复状态机 |
| 上下文污染 | 假设、噪音、过期信息混入事实 | 事实/假设/废弃分层；证据引用；Context 筛选 |
| 权限越界 | 读写混合、模型直接执行、缺确认 | 最小权限、读写拆分、审批节点、审计 |
| 不可恢复错误 | 工具仅返回模糊错误信息 | 结构化错误码、是否可恢复、建议下一步、重试规则 |
| 提示注入与数据泄露 | 不可信内容影响指令或外传敏感信息 | 指令/数据分离、不可信输入标记、来源限制、脱敏和权限门 |

### 8.1 风险分级与审批

一种实用划分是：

- 低风险：只读查询，可在受限范围内自动执行；
- 中风险：生成草稿、计划、patch，可自动生成但不应自动提交；
- 高风险：写入、删除、命令执行、外发、发布、修改权限，必须经策略判定和用户确认。

权限规则需要优先级明确。例如拒绝规则必须能覆盖较宽松的允许规则；“信任工作区”也不应等同于无限制
执行。每次高风险调用应记录触发者、目标、前置状态、审批决定、实际参数、结果和可关联的审计 ID。

### 8.2 恢复不是无限重试

恢复策略要与错误语义相匹配：缺输入时向用户提问；可重试的临时故障有限重试并采用退避；权限不足时
停止并说明；无数据时调整范围或透明报告；预算耗尽时保存状态并输出阶段性结果。禁止把“换一个工具绕过
权限”当作恢复。

## 9. 可观测性与评估：结果正确还不够，轨迹也要可信

### 9.1 Agent Trace 与普通日志的区别

传统日志主要回答“接口是否成功、耗时多少”；Agent Trace 还要回答“为什么选这条路径、看到了什么、
为何相信这个结论”。HTTP 全部返回 200 时，Agent 仍可能已在第一步误解目标。

每条 Trace 建议至少关联以下事件：

```text
run / session / task id
目标与成功标准
模型、提示词、Skill 与工具版本
每轮上下文来源及压缩/截断决定
计划或路由决定、状态 diff
工具选择、参数、权限判定、耗时、重试与返回摘要
预算（步骤、Token、时间、成本）
证据被最终结论引用的关系
验证器 / 评估结果、取消或人工接管原因
```

工具问题的排查应分段：工具选择 → 参数生成 → 权限检查 → 工具服务执行 → 结果理解。不同分段对应不同
修复位置：工具描述/路由、Schema、策略门、服务韧性或证据/输出校验，而不是统称为“模型幻觉”。

### 9.2 任务结果的四级分类

仅统计“是否有答案”会掩盖高风险失败。更有意义的分类是：

| 结果 | 含义 |
| --- | --- |
| 完整完成 | 目标满足，证据和必要验证充分 |
| 部分完成 | 已取得部分可靠结果，明确剩余缺口 |
| 正确失败 | 无法继续时正确追问、停止或说明限制，没有伪造事实 |
| 错误失败 | 未完成且编造、越权或给出无证据结论 |

对于研究项目，“正确失败率”和“错误失败率”通常比单一成功率更能体现 Agent 是否值得信任。

### 9.3 指标体系

| 维度 | 可测指标 |
| --- | --- |
| 任务效果 | 完整完成、部分完成、正确失败、错误失败比例；证据充分性 |
| 效率 | 平均决策步数、关键路径长度、无效/重复调用率、墙钟时间、Token 和费用 |
| 工具质量 | 工具选择、参数、调用时机、结果理解正确率；schema 拒绝率 |
| 恢复能力 | 按错误类型统计合理转向率、有限重试成功率、优雅停止率 |
| 安全 | 未审批高风险调用数、权限绕过尝试、敏感信息泄露、审计完整性 |
| 运行健康 | 超时、取消、工具失败、上下文压缩、预算耗尽、人工接管率 |

评估集不能只含“信息完整、工具可用”的顺利任务；应同时覆盖信息缺失、工具超时/无数据/权限不足、高风险
动作、噪音与提示注入干扰。自动化规则适合判定 schema、步骤、违规调用和错误恢复；人工抽检更适合判断
证据链、结论质量、可执行性与风险遗漏。LLM-as-judge 可辅助，但不应成为安全或事实正确性的唯一裁判。

### 9.4 把失败转化为 Harness 资产

每次可复现失败至少应沉淀为四类资产：

1. **归因**：是目标、上下文、工具、参数、权限、服务、状态还是验证问题；
2. **回归样本**：固定输入、环境、允许动作、预期结果和评分规则；
3. **结构性规则**：如连续失败停止、危险操作审批、关键证据必需；
4. **监控信号**：如重复调用、成本突增、关键证据缺失、工具错误率异常。

这样改进不是“改 Prompt 后感觉好一点”，而是可回归、可量化、可解释的研究循环。

## 10. Coding Agent 的专门启示

对代码任务，核心循环通常是：理解请求 → 浏览/检索仓库 → 定位证据 → 形成计划 → 修改或生成 patch →
运行相关验证 → 根据失败修正 → 汇报 diff、验证结果与剩余风险。

从材料中的 Coding Agent 案例可提炼出以下可迁移原则：

1. **专用工具优先于通用 Shell**：读取、搜索、编辑、查看 diff、执行测试使用语义明确的工具，Shell 留给
   无法替代的场景。这有利于权限、审计、UI 反馈和错误处理。
2. **编辑要可审查**：优先精确 patch/diff；将“生成草稿”和“真正写入”分离；写后再读和测试验证。
3. **仓库指令是受限上下文**：项目规则应可复用、接近任务、低于系统安全规则；不可因为项目指令覆盖
   权限边界。
4. **探索与决策分离**：用只读、低权限或低成本子 Agent 收集信息，向主 Agent 返回压缩摘要与证据，
   避免大批文件和日志挤满主会话。
5. **上下文压缩并非记忆**：工具结果裁剪、会话摘要和必要时 context reset 应与外部状态/checkpoint 配合；
   否则长任务会忘记关键限制与已修改文件。
6. **默认验证真实环境结果**：模型说“修复完成”不能替代测试、静态检查、diff 审查或用户审批。
7. **先建立安全默认值**：只读优先、权限最小化、危险命令显式确认、取消可恢复、操作可追溯。

## 11. 面向 RepoPilot 的研究整理矩阵

RepoPilot 的定位是本地运行的 Agent 研究项目。因此，本笔记建议下一阶段把“功能是否存在”与“该机制是否
带来可测收益”严格分开。下表是从资料到实验的映射，不代表每一项必须立刻实现。

| 知识主题 | 可研究的问题 | 自变量 / 对照 | 主要观测指标 | 适合的 RepoPilot 产物 |
| --- | --- | --- | --- | --- |
| Loop 预算 | 预算能否减少无效探索而不显著降低任务完成？ | 不同 step/Token/时间上限 | 完成分级、重复调用率、成本、优雅停止率 | 预算消融任务集与 Trace 对比 |
| 状态外化 | 显式 State 是否比纯聊天历史更抗中断与长上下文？ | transcript-only vs session state/checkpoint | 恢复成功率、遗漏率、重复读文件率 | 中断—恢复基准与状态 schema |
| Context 策略 | 选择/压缩/重置分别如何影响代码任务？ | 全量历史、摘要、JIT 检索、context reset | 任务质量、Token、证据保留率 | Context 消融报告 |
| 工具 Schema | 严格参数与结构化错误是否减少误调用？ | 宽松文本参数 vs enum/required/error contract | 参数错误、恢复正确率、越权尝试 | 工具契约负例测试 |
| 权限系统 | 审批如何改变安全性与用户中断成本？ | manual、accept-edits、plan 等模式 | 未授权副作用、审批次数、完成时间 | 安全测试矩阵与审计 trace |
| 检索策略 | 代码任务何时应使用文本/符号检索，何时应加入 RAG？ | grep/glob/AST、BM25/RAG、混合 | 定位准确率、Token、可解释性、延迟 | 代码检索消融实验 |
| Reviewer / Reflection | 独立校验器是否改善最终 patch 质量？ | 无 reviewer、同模型 reviewer、规则验证 | 测试通过、错误接受率、额外成本 | patch 评审基准 |
| 子 Agent | 并行探索是否在大仓库中有净收益？ | 单 Agent、只读子 Agent、全能力子 Agent | 墙钟时间、主上下文占用、汇总错误 | 任务包与汇总协议实验 |
| Graph 编排 | 显式节点/边是否提升恢复与可解释性？ | 单 Loop、图中规则节点、模型路由节点 | 路由错误、checkpoint 恢复、trace 清晰度 | 最小可执行 graph 任务 |
| 失败闭环 | 把真实失败纳入回归集是否能防止复发？ | 无回归、Prompt-only、Harness-rule + regression | 同类失败复发率、指标变化 | failure corpus 与回归报告 |

研究设计注意事项：固定模型版本、提示词、工具集、权限模式、预算和初始仓库状态；记录随机性设置；将
“模型调用失败/服务故障”和“Agent 决策失败”分开；报告完整完成、正确失败和安全违规，而非只挑成功
案例展示。

## 12. 可直接使用的检查表

### 12.1 新增一个 Agent 能力前

- [ ] 这是开放路径问题吗？固定 Workflow 是否已足够？
- [ ] 目标、成功标准、风险边界与停止条件是否可写清？
- [ ] 新工具是否有明确名称、Schema、范围、结构化成功/失败返回？
- [ ] 它是只读、草稿还是副作用能力？副作用是否需要确认？
- [ ] 需要保存哪些 State，而不是哪些聊天原文？
- [ ] 是否能为该能力写正常、缺参、超时、权限不足和干扰样本？

### 12.2 一次 Agent 运行异常后

- [ ] Trace 中能否定位目标、路由、上下文、工具、权限、服务或结果理解的哪一段出错？
- [ ] 是否存在重复调用、预算耗尽、未验证假设或上下文污染？
- [ ] 正确行为本应是继续、重试、降级、追问、暂停还是停止？
- [ ] 是否将失败样本加入回归评测？
- [ ] 是否需要修改工具契约、状态 schema、权限规则、验证器或监控，而不仅是 Prompt？
