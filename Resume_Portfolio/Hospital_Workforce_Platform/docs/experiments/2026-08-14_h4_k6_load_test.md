# 实验记录：H4 真实数据 k6 压测

## 1. 目标与边界

在 Compose 全链路中，使用真实 Keycloak HR_ADMIN token 对排班分页查询进行 5 分钟并发
压测。数据不是 mock：固定 50 名员工、每人 20 个班次，共 1,000 条 2026-09 排班。

本实验验证的是单机容器环境下的已认证读路径，不代表公网延迟、写吞吐或生产容量上限。

## 2. 环境

- CPU：13th Gen Intel Core i9-13980HX，24 核 / 32 逻辑处理器；
- 主机内存：33,959,837,696 bytes（约 31.63 GiB）；
- Docker 可用内存：15.43 GiB；
- Docker Desktop 4.82.0 / Engine 29.6.1 / API 1.55，Linux amd64；
- k6 2.1.0，镜像 digest：`sha256:65c920dc067d5e2e00befbf982af6ad6ad0117034e8b1c65817c7975c52d4669`。

## 3. 数据准备与命令

```powershell
$seed = .\scripts\seed-performance.ps1 -EmployeeCount 50 -ShiftsPerEmployee 20
$env:DEPARTMENT_ID = [string]$seed.DepartmentId
$env:ACCESS_TOKEN = '<HR_ADMIN access token>'
docker compose --profile perf run --rm load-test `
  run --summary-export=/results/formal-summary.json /scripts/scheduling.js
```

负载模型：30 秒线性升至 25 VU，4 分钟线性升至 100 VU，30 秒降至 0；每个 VU 每秒
查询一次 `2026-09-01` 至 `2026-10-01` 的排班分页。阈值为错误率 `<1%`、p95 `<300ms`。

## 5. 资源采样

`docker stats --no-stream` 在运行期间采样：

| 时点 | VU | backend CPU / RAM | MySQL CPU / RAM | k6 RAM |
|---|---:|---|---|---|
| 中段 | 约 70 | 10.94% / 764.9 MiB | 12.37% / 483.5 MiB | 42.52 MiB |
| 峰值附近 | 99 | 10.25% / 727.5 MiB | 10.16% / 483.2 MiB | 46.23 MiB |

这些是瞬时样本而非时间序列分位数，因此不据此声称峰值 CPU 或稳定内存上限。

## 6. Pilot 与正式结果隔离

第一次 5 分钟 pilot 对空结果页完成 16,771 次请求、0 错误，但由于查询科室没有落在窗口
内的班次，不能作为正式性能证据，保留为 `pilot-empty-summary.json`。随后使用固定脚本创建
1,000 条班次，并验证 API 返回 `totalElements=1000`、首屏 20 条，才执行本次正式实验。

15 秒、5 VU smoke 结果保留为 `smoke-summary.json`，仅用于验证脚本和环境。

## 7. 结论

H4 阈值在上述单机、真实认证、1,000 条排班的读场景下通过。简历可引用正式结果，但必须
同时保留数据规模、请求类型与单机容器边界。
