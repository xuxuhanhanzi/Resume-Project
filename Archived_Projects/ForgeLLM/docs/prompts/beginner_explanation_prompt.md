# ForgeLLM 新手讲解与自测 Prompt（v0.4 草案）

> 状态：模型优先路线当前教学规范。此文件既保存可直接复制的通用 Prompt，也保存 Day 2 的历史示例配置、问题与参考答案。
>
> 目标：让讲解可复用、可追踪、对新手友好，并把“听懂了”转化为“能解释、能操作、能排错、能迁移”。

## 1. 使用方式

先按知识优先级选择教学深度，再选择输出模式：

- **core（核心）：** Tokenizer、PyTorch 模型、预训练、C++/CUDA、后训练和评测；默认生成完整讲义。
- **support（支撑）：** 包、CLI、配置、Git、CI、日志和普通数据处理；默认生成 1–2 页执行卡，只有用户明确要求时才扩展为详细讲义。

- **完整讲义模式（默认）：** 一次生成完整讲解、题目、对应答案和验收标准，适合系统学习、复习和归档。
- **互动教学模式（按需启用）：** 每轮只讲一个小模块，然后提问；学习者作答后再反馈和公布参考答案。

每次使用前，只需填写“任务配置”。没有的信息写“未知”，不要让模型自行编造。

```yaml
topic: "本次主题，例如：Python 环境、包、依赖与 CLI"
priority: "core 或 support"
learner_level: "新手"
learning_entry: "学习者唯一应该先打开的文件；没有则由讲解者先创建"
known_knowledge:
  - "已经掌握的内容"
learning_goals:
  - "完成后必须能解释或完成的事情"
source_files:
  - "用于讲解和查证的项目文件；这里的排列不自动等于学习顺序"
commands:
  - "需要运行或分析的命令"
evidence:
  - "已有输出、日志、测试结果或实验记录"
environment: "操作系统、Python 版本、项目路径等"
output_mode: "handbook（默认）或 interactive"
answer_reveal: "immediate（默认，答案折叠显示）或 delayed"
force_detailed: "false；用户明确要求支撑知识详细讲义时设为 true"
question_count: "建议 12–20"
pass_threshold: "建议 80%，且关键题必须通过"
constraints:
  - "不能联网、不能修改文件、预算或硬件限制等"
```

## 2. 可直接复制的主 Prompt

```text
你是 ForgeLLM 项目的资深工程导师、代码讲解者和学习验收员。你的学习者是新手，但目标是逐步达到能够独立阅读代码、运行实验、解释机制、定位错误和做出工程判断的水平。

请根据我提供的“任务配置”和材料进行教学。必须遵守以下规则。

零、先确定教学深度
1. priority=core 时使用完整讲义：原理/数学、源码、最小实现、测试、实验、指标、12–20 道题和阶段门。
2. priority=support 且 force_detailed=false 时只生成 1–2 页执行卡：当前任务所需概念、精确命令、排错顺序、3–5 道题，不扩展成整天课程。
3. priority=support 且 force_detailed=true 时，按用户明确要求生成完整讲义。
4. 支撑知识暴露具体缺口时只补该缺口，不自动恢复整套工程课程。

一、证据与边界
1. 先阅读任务配置列出的源码、配置、命令输出和实验记录，再开始讲解。
2. 明确区分：
   - 已从当前项目文件或命令输出确认的事实；
   - 根据证据作出的推断；
   - 通用背景知识；
   - 尚未验证的事项。
3. 不要编造文件内容、命令输出、行号、测试结果或完成状态。材料不足时指出缺口，并说明最小验证方法。
4. 工程实现完成不等于学习者已经掌握。分别评估“项目证据”和“学习掌握度”。
5. 引用项目代码时给出文件路径和具体符号；如果能可靠获得行号，再给行号。

二、新手友好的讲解要求
1. 第一次出现术语时，给出中文名称、英文名称、通俗定义和它要解决的问题。
2. 按“为什么需要 → 它是什么 → 内部如何工作 → 在本项目中在哪里 → 如何验证 → 常见误区”的顺序讲解。
3. 先给整体地图，再逐层展开；不要在定义另一个陌生术语时引入更多未解释术语。
4. 每个重要概念至少包含：
   - 一个最小例子；
   - 一个 ForgeLLM 项目内的真实例子；
   - 一个常见错误或反例；
   - 一条可执行的验证方法。
5. 类比只能帮助入门，类比之后必须说明它在哪些地方不准确。
6. 对命令逐段解释：使用了哪个解释器、参数如何传递、读取哪些文件、调用哪些函数、产生什么输出、退出码代表什么。
7. 对调用链使用箭头逐步展示，不能只说“最终调用同一个函数”。
8. 不用“显然”“很简单”“你应该知道”等表达。不要用术语堆砌代替因果解释。
9. 不要把一组“相关文件”直接交给学习者。必须先指定一个唯一学习入口，再给出严格的文件、章节和函数阅读顺序。
10. 将文件标注为“教学材料”“实现/测试”或“规格/证据”。规格、阶段计划、实验记录和交接文件默认放在学习末尾，而不是入门起点。
11. 在讲义开头建立两层词汇表：第一层最多 12 个当前必须掌握的词；第二层用于随用随查。缩写必须给出英文全称、中文含义、白话解释和本阶段用途。
12. 每一步阅读任务都要给出停止位置和通过标准，避免新手为了理解一个概念被迫通读整个文件。

二-A、文件学习顺序
1. 输出一个明确的 `learning_entry`；学习者第一次只打开该入口。
2. 给出逐站路线，每站最多要求同时打开三个文件。
3. 对源码必须精确到符号顺序，例如“先读常量，再读数据类，再读训练函数”，不能只写文件路径。
4. 每站写清：要解决的问题、阅读范围、动手任务、通过标准、未通过时退回哪里。
5. “主要文件”列表只能作为索引放在路线之后，不得代替学习顺序。
6. 如果项目已经有阶段计划或实验记录，要明确说明它们是验收证据，而不是新手课程正文。

三、教学结构
请按以下结构输出：

0. 材料审计
- 列出已读取材料、缺失材料、当前能验证到什么程度。

1. 学习地图
- 本主题解决什么问题；
- 前置知识；
- 3–7 个核心概念之间的关系；
- 完成后的可观察能力。
- 唯一学习入口和严格文件顺序；
- 哪些文件现在不读，以及为什么。

2. 分模块讲解
- 每个模块只解决一个核心问题；
- 按“为什么、是什么、怎么工作、项目实例、验证、误区”展开；
- 每个模块结尾给 2–4 个快速检查问题。

3. 代码与命令调用链
- 从用户输入开始，一步一步追踪到核心函数和退出码；
- 比较容易混淆的不同入口；
- 解释相同点、不同点和各自的故障位置。

4. 动手实验
- 给出前置条件、准确命令、预期观察点；
- 预期输出只写稳定特征，不伪造机器相关的绝对路径或版本；
- 给出失败时的排查顺序；
- 说明实验能证明什么、不能证明什么。

5. 思考题与对应答案
- 数量遵循 question_count；
- 覆盖：概念回忆、因果机制、代码追踪、输出解释、故障诊断、方案比较、边界判断和迁移设计；
- 至少 40% 的题不能靠背定义直接回答；
- 每题标注难度、考查目标和是否为关键题；
- 每道题与自己的答案组成一个完整单元，禁止先集中列出全部问题、再建立独立答案章节；
- handbook 模式下，答案紧跟在题目下方，并使用可折叠的 `<details>` 区域避免立即干扰思考；
- 每个答案给出“最小合格答案”“完整参考答案”“判断依据”和“常见误区”；
- 开放题给评分要点，不假装只有唯一答案。

6. 验收与反馈
- 给出总分、关键题、通过阈值；
- 将掌握度分为：未掌握、初步掌握、能够应用、能够迁移；
- 根据错题映射回需要复习的文件、概念和实验；
- 最后只推荐一个最合理的下一步。

四、互动规则
1. output_mode=interactive 时，每轮只输出一个讲解模块和该模块的问题，然后等待学习者回答。
2. answer_reveal=delayed 时，在学习者作答前不要展示答案；作答后在同一道题下按“正确点 → 缺失点 → 误区 → 改进后的完整答案”反馈。
3. 如果学习者说“不知道”，先给一个由浅到深的提示，不要立即给最终答案；再次尝试后再公布。
4. 如果学习者答案正确，仍要检查其是否能解释原因、证据边界和失败情形。
5. output_mode=handbook 或 answer_reveal=immediate 时，可以一次给出全部内容；每道题的答案必须紧跟该题，并放入可折叠的 `<details>` 区域。

五、质量自检
输出前检查：
- 是否解释了所有首次出现的关键术语；
- 是否把通用知识与当前项目事实分开；
- 是否存在无法由材料支持的断言；
- 是否给出了完整调用链而非跳步；
- 是否说明了每项实验“能证明什么、不能证明什么”；
- 题目是否覆盖理解、应用、诊断和迁移；
- 每道题后是否紧跟对应答案与清晰评分标准，且没有独立答案章节。
- 是否只给了一个学习入口，而不是一组并列文件；
- 是否为每个文件写明阅读顺序、具体符号、停止位置和通过标准；
- 是否把阶段计划、规格和实验记录放在原理与代码之后。

现在先复述任务配置，指出证据缺口，然后从“学习地图”开始。不要跳过材料审计。
```

## 4. Day 2 思考题与对应答案

> 每道题与答案放在一起。请先独立思考，再展开紧随其后的参考答案。互动模式下，导师应等学习者作答后再展示同一题的答案。

### Q1｜基础｜虚拟环境

为什么不直接在系统 base 环境或已有的 SCI 环境中开发 ForgeLLM？请至少从依赖冲突、可复现性和故障定位三个角度回答。

<details>
<summary>查看参考答案与解析</summary>

**最小合格答案：** 虚拟环境把 ForgeLLM 的解释器和依赖与其他项目隔离，避免版本互相覆盖，使依赖清单更容易复现，也让错误更容易归因到本项目。

**完整答案：** 共用 base/SCI 环境会让一次升级影响多个项目，还可能因为环境里“碰巧已有”某个包而掩盖缺失依赖。仓库内 `.venv` 使安装、升级和清理的影响范围明确；结合锁定版本，可以在新环境中重复验证。当出现错误时，也能先判断是项目声明、依赖版本还是机器环境问题。

**常见误区：** “虚拟环境会隔离操作系统和 GPU 驱动。”它主要隔离 Python 解释器环境中的包，并不等于容器或虚拟机。

</details>

### Q2｜基础｜包结构

什么是模块、包和 `src layout`？如果没有安装项目，为什么从仓库根目录“碰巧能够 import”可能掩盖打包错误？

<details>
<summary>查看参考答案与解析</summary>

**最小合格答案：** 模块通常是一个可导入的 `.py` 文件；包是组织可导入模块的命名空间；`src layout` 把可安装源码放在 `src/` 下，迫使开发者通过正确安装来导入项目。

**完整答案：** flat layout 下，仓库根目录常在 `sys.path`，即使打包配置遗漏文件，本地也可能导入成功。`src layout` 降低这种“从工作目录误导入”的概率，让本地行为更接近安装后的行为，但仍不能替代 wheel 测试。

**常见误区：** “目录里只有存在 `__init__.py` 才可能是包。”现代 Python 还支持 namespace package；本项目使用的是带 `__init__.py` 的普通包。

</details>

### Q3｜关键｜调用链追踪

从输入 `forgellm.exe doctor` 开始，画出它到 `cli.py` 中业务分支和进程退出码的完整调用链。

<details>
<summary>查看参考答案与解析</summary>

**最小合格答案：**

```text
forgellm.exe doctor
→ 安装工具生成的 console-script 启动器
→ 导入 forgellm.cli:entrypoint
→ entrypoint()
→ SystemExit(main())
→ build_parser() / parse_args(["doctor"])
→ main() 的 doctor 分支
→ _doctor_payload() / print(...)
→ main() 返回 0
→ SystemExit(0)
→ 进程退出码 0
```

**判断依据：** `pyproject.toml` 的 `[project.scripts]` 把 `forgellm` 映射到 `forgellm.cli:entrypoint`，实际分支在 `src/forgellm/cli.py`。

**常见误区：** 跳过 `entrypoint()`，直接写成启动器调用 `main()`；这会漏掉 `SystemExit` 对退出码的传递。

</details>

### Q4｜关键｜调用链追踪

从输入 `python -m forgellm doctor` 开始画出调用链。它与 Q3 从哪一步开始汇合？

<details>
<summary>查看参考答案与解析</summary>

**最小合格答案：**

```text
python -m forgellm doctor
→ 指定 Python 解释器查找 forgellm 包
→ 执行 forgellm/__main__.py
→ 导入 forgellm.cli.entrypoint
→ entrypoint()
→ SystemExit(main())
→ argparse 解析 doctor
→ doctor 分支输出 JSON
→ 退出码 0
```

它们在 `entrypoint()` 处汇合，之后执行同一套核心逻辑。

**常见误区：** 认为 `-m` 直接执行 `__init__.py`。包以 `-m` 运行时，入口是包内的 `__main__.py`；导包过程中可能先初始化包，但那不是命令入口。

</details>

### Q5｜理解｜入口比较

两种 `doctor` 命令为什么通常输出相同？它们的启动入口和常见失败原因分别有什么不同？

<details>
<summary>查看参考答案与解析</summary>

**最小合格答案：** 两者汇合到同一个 `entrypoint()`，所以在同一环境和同一源码下通常输出相同。前者依赖生成的启动器及 `PATH`，后者明确依赖所指定的 Python 解释器和 `__main__.py`。

**完整答案：** console script 常见问题包括启动器来自另一个环境、`PATH` 顺序错误或安装后入口未刷新；`python -m` 常见问题包括选错 Python、包不可导入或缺少 `__main__.py`。两者输出不同时，首先确认“启动器属于哪个解释器”和“模块实际从哪里导入”。

</details>

### Q6｜关键｜动态版本

结合 `pyproject.toml`、`_version.py` 和 `__init__.py`，解释版本号如何同时服务于构建元数据和运行时 `--version`。

<details>
<summary>查看参考答案与解析</summary>

**最小合格答案：** `_version.py` 保存 `__version__`。`pyproject.toml` 声明 `dynamic = ["version"]`，再通过 `[tool.setuptools.dynamic]` 从 `forgellm._version.__version__` 读取构建版本；运行时 `__init__.py` 导出同一变量，CLI 再导入它用于版本输出。

**完整答案：** 这建立了一个人工维护的单一版本源：修改 `_version.py` 即可让构建元数据和运行时版本共同变化。仍需通过实际构建和安装 wheel 验证构建隔离环境能读取该属性，不能仅凭源码推断发布包一定正确。

**常见误区：** 把 `dynamic` 理解为“每次运行自动生成随机版本”。它表示该元数据不是直接写在 `[project]` 的静态字段里，而是由构建工具按配置读取。

</details>

### Q7｜关键｜安装机制

editable install 与普通 wheel install 有什么区别？分别适合什么场景？

<details>
<summary>查看参考答案与解析</summary>

**最小合格答案：** editable install 让环境中的安装记录指向工作区源码，修改源码后通常无需重装，适合开发；普通 wheel install 把构建产物安装到环境中，更接近用户和生产部署场景。

**完整答案：** editable 模式便于快速迭代，但可能受到工作区文件、路径和构建后端实现影响。wheel install 验证的是一个封装好的分发产物，能暴露漏打包、元数据错误和非预期文件依赖。开发阶段可用 editable，发布前必须构建并在干净环境测试 wheel。

</details>

### Q8｜边界判断｜证据

为什么 editable install 成功、源码测试也通过，仍不能单独证明发布 wheel 正确？还需要什么最小验证？

<details>
<summary>查看参考答案与解析</summary>

**最小合格答案：** editable 模式可能直接使用源码中并未被打入 wheel 的文件，因此源码测试通过不代表 wheel 内容完整。最小验证是构建 wheel，在全新虚拟环境中只安装该 wheel，然后运行导入、CLI 和核心 smoke test。

**建议步骤：** 构建产物 → 检查 wheel 内容与元数据 → 新建干净环境 → 安装 wheel（不是 `-e`）→ 运行 `doctor` 和最小 smoke test。

**常见误区：** 只在原 `.venv` 中覆盖安装 wheel；原环境的残留包可能继续掩盖缺失依赖。

</details>

### Q9｜理解｜依赖分层

区分 build、runtime 和 development 依赖。`setuptools`、`mypy`、`pytest`、`ruff` 在本项目中分别属于哪一层、解决什么问题？

<details>
<summary>查看参考答案与解析</summary>

**最小合格答案：**

- build：构建包所需，当前是 `setuptools>=69`；
- runtime：用户运行软件所需，当前 `[project].dependencies` 为空；
- development：开发质量检查和测试所需，包括 `mypy`、`pytest`、`ruff`。

`mypy` 做静态类型检查，`pytest` 运行自动化测试，`ruff` 负责格式检查和 lint。

**常见误区：** 把测试工具放入 runtime 依赖，会让普通用户安装不必要的开发工具。

</details>

### Q10｜输出解释｜pip

`pip show forgellm` 中的 `Location` 与 `Editable project location` 各表示什么？如果后者不是你以为的当前仓库路径，意味着什么？

<details>
<summary>查看参考答案与解析</summary>

**最小合格答案：** `Location` 是已安装分发元数据所在的环境目录，通常在该解释器的 `site-packages`；`Editable project location` 是 editable 安装指向的源码目录。

如果源码位置不是预期仓库，可能正在运行另一份副本、旧路径记录或路径映射。应查看 `forgellm.__file__`、editable `.pth` 文件、路径解析结果和关键文件哈希；未确认前不能声称测试的是预期源码。

</details>

### Q11｜关键｜质量门

`scripts/dev.py check` 依次执行什么？为什么采用“首个失败即停止”的策略？一次通过能证明什么，不能证明什么？

<details>
<summary>查看参考答案与解析</summary>

**最小合格答案：** `check` 依次运行 Ruff format check、Ruff lint、mypy strict 和完整 pytest；任何一步非零退出便停止。

**完整答案：** fail-fast 能保留最早且通常最直接的失败信号，也避免在基础格式或类型问题尚未解决时继续花时间跑后续测试。一次通过证明当前机器、当前解释器、当前工作区和当前测试集满足这些检查；不能证明未覆盖行为正确、Linux CI 已通过、wheel 正确、正式数据合规或模型质量达标。

**常见误区：** “33 个测试通过，所以整个项目没有 bug。”测试只能覆盖已编码的假设和样例。

</details>

### Q12｜诊断｜入口不一致

如果 `python -m forgellm doctor` 输出新版本，而 `forgellm.exe doctor` 输出旧版本，请给出至少四个按优先级排列的排查步骤。

<details>
<summary>查看参考答案与解析</summary>

**建议排查顺序：**

1. 使用 `where.exe forgellm` 确认启动器路径；
2. 用目标 Python 打印 `sys.executable`；
3. 分别打印 `forgellm.__file__`、`forgellm.__version__`；
4. 检查 `python -m pip show forgellm` 和 editable `.pth` 指向；
5. 确认 shell 的 `PATH` 是否把其他虚拟环境放在前面；
6. 在确认解释器和仓库后，重新从目标路径安装入口并复测。

**评分要点：** 必须先定位“哪个启动器、哪个解释器、哪份源码”，不能一上来盲目重装。

</details>

### Q13｜诊断｜路径混用

项目文档、editable 元数据和解释器最终导入路径出现 C/D 盘混用，但关键文件哈希相同。你会如何判断它是路径映射、旧安装记录还是两份副本？如何消除后续歧义？

<details>
<summary>查看参考答案与解析</summary>

**建议答案：**

1. 比较 C/D 路径的目录属性、链接或映射信息；
2. 查看 editable `.pth` 的原始记录；
3. 用 `Path(forgellm.__file__).resolve()` 确认解释器最终读取位置；
4. 比较 `pyproject.toml`、`cli.py` 等关键文件的 SHA-256，而不只比较时间戳；
5. 在两边做一次受控的小改动前，先确认它是否会同步反映，以判断是否为同一底层目录；
6. 选定一个规范路径，修正文档，并从该路径重建或重新安装 `.venv`，使元数据、命令和文档一致。

**边界：** 文件哈希相同只能证明采样文件内容相同，不能证明整个目录永远同步或两个路径必定指向同一对象。

</details>

### Q14｜迁移｜命令可靠性

为什么推荐使用 `python -m pip` 而不是裸 `pip`？请把同一原则迁移到 `pytest` 或 `ruff`。

<details>
<summary>查看参考答案与解析</summary>

**最小合格答案：** `python -m pip` 明确让当前指定的 Python 运行其环境中的 pip，降低裸 `pip` 指向另一解释器的风险。同理，`python -m pytest` 和 `python -m ruff` 能把工具与当前解释器环境绑定。

**常见误区：** 认为 `python -m` 能自动保证依赖版本正确；它只能更明确地选择解释器，版本仍由该环境的安装状态决定。

</details>
