# 第一个月详细执行计划：工程基线、数据与 Tokenizer

## 1. 本月定位

第一个月只推进 `ForgeLLM`，不并行开发 `RepoPilot`。本月目标不是训练出“效果很好”的模型，而是建立后续训练能够依赖的、可测试和可复现的地基。

当前资源按 **4 周、每周 60 小时以上**执行。核心 P0 仍按约 35 小时/周控制，额外时间用于原理学习、测试、复现、失败分析和 P1；不能通过减少验收步骤来提前进入后续阶段。

资源卡未填写前，只运行 CPU Smoke Test；长训练、付费数据下载和云 GPU 任务都不启动。

### 本月完成定义

月底同时满足以下条件，才进入 Decoder-only Transformer 阶段：

- 新环境可按 README 命令完成安装、静态检查、单元测试和 CPU Smoke；
- Python 包、配置、日志、实验记录和 Artifact 路径约定已经稳定；
- 一个正式数据源完成来源、许可证、哈希、清洗规则、统计与局限记录；
- 手写最小 BPE 通过确定性、保存/加载、编码/解码和边界测试；
- 正式 Tokenizer 可训练、可复现、可评测，并输出冻结的词表与报告；
- `docs/month_01_progress.md` 中 P0 项全部完成，G0 与 G1 门禁通过；
- 形成 `v0.1-engineering` 和 `v0.2-data-tokenizer` 两个可审计发布切片。

## 2. 本月需要学习并掌握的内容

| 知识模块 | 必须理解 | 必须能做 | 本月证据 |
|---|---|---|---|
| Python 工程 | 包结构、`pyproject.toml`、虚拟环境、锁定依赖、CLI、异常边界 | 从空环境安装项目并执行统一命令 | 安装说明、CI、CPU Smoke |
| 测试与质量 | 单元/集成/Smoke 的区别，测试夹具，确定性，边界与失败测试 | 为核心函数先定义可验证行为 | 测试报告与失败用例 |
| 可复现性 | 随机种子、环境快照、Git 状态、配置快照、Artifact 命名 | 让一次运行可由命令、配置和 Run ID 反向定位 | 实验记录和运行目录 |
| LLM 数据工程 | 文本读取、Unicode 规范化、质量过滤、去重、切分、污染、PII、许可证 | 对单一数据源生成清洗后语料、manifest 和统计报告 | Data Card、manifest、报告 |

### 本月不要求掌握

- 不开始 Transformer 模型实现、预训练、LoRA、DPO 或 Agent；
- 不引入 FSDP、DeepSpeed、vLLM、Kubernetes、MLflow 服务端；
- 不为“以后可能需要”提前堆叠数据库、消息队列或复杂配置框架；
- 不使用大规模数据或 GPU 结果代替 CPU 下的正确性证明。

## 3. 逐周实施计划

## 第 1 周：工程契约与本地开发闭环

**目标：** 把骨架变成可安装、可检查、可测试的 Python 项目。

### Day 1：资源与范围冻结（3–4h）

- 填写 `docs/project_resource_card.md`：时间、周期、GPU、显存、预算、存储和岗位优先级；
- 盘点本机 Python、Git、Docker、GPU/CUDA 状态，但不立即升级环境；
- 写第 1 阶段计划，确定本月唯一主线和停止清单；
- 选择包导入名、最低 Python 版本和支持平台，记录为 ADR。

**学习：** 环境隔离、语义化版本、ADR、P0/P1/P2 范围控制。  
**产物：** 已填写资源卡、环境盘点、阶段计划、ADR。  
**退出条件：** 未知资源不再影响 CPU 主线；所有 GPU 工作都标明触发条件。

### Day 2：包与依赖基线（4–6h）

- 建立 `src/forgellm/` 包、版本入口和最小 CLI；
- 配置核心依赖与开发依赖，固定安装方式；
- 配置格式、lint、类型检查和测试工具；
- 保持依赖最小化，每个依赖在阶段计划中说明用途。

**学习：** `pyproject.toml`、editable install、入口点、依赖上下界。  
**产物：** 可安装包、`forgellm --help`、开发命令。  
**测试：** 空环境安装；导入测试；CLI 帮助测试。

### Day 3：配置、日志与 Run ID（4–5h）

- 定义轻量配置读取与校验，不在首月引入重量级平台；
- 定义日志格式、错误退出码和随机种子入口；
- 定义 `run_id`、只读解析后配置、环境快照和 Artifact 目录；
- 禁止在日志中写 Secret、完整凭据和未经确认的原始敏感文本。

**学习：** 配置优先级、结构化日志、可重复随机性、数据血缘。  
**产物：** 一个仅生成运行元数据的 CPU Smoke。  
**测试：** 相同输入产生一致配置；非法配置快速失败；敏感字段被脱敏。

### Day 4：测试分层与统一命令（4–5h）

- 建立 `tests/unit`、`tests/integration`、`tests/smoke`；
- 在 Makefile 或跨平台脚本中提供 setup、lint、typecheck、test、smoke 命令；
- 测试临时目录与固定种子，不污染仓库内正式 Artifact；
- 记录一次故意失败并修复的过程，验证失败输出可读。

**学习：** 测试金字塔、fixture、参数化测试、退出码。  
**产物：** 本地质量命令与最小测试套件。

### Day 5：CI 与陌生环境复现（4–6h）

- CI 在受支持的 Python 版本上执行安装、lint、类型检查、测试和 CPU Smoke；
- 缓存只用于加速，不得成为正确性前提；
- 更新 README 的 5 分钟 Quickstart、预期输出和常见失败；
- 在一个新虚拟环境中按 README 从头复现。

**产物：** `v0.1-engineering` 候选。  
**周门禁 G0：** 新环境一次通过；无手工改文件步骤；命令、配置、日志和报告能互相定位。

### 第 1 周失败处理

- Windows/Linux 差异导致 Makefile 不可用：以 Python CLI 作为权威入口，Makefile 只做代理；
- 依赖冲突超过半天：删减非必要依赖，暂不加入训练框架；
- Docker 不可用：不阻塞 G0，记录为第 2 周 P1，先确保本机隔离环境可复现。

## 第 2 周：数据流水线最小闭环

**目标：** 对极小夹具数据建立 `read → normalize → filter → deduplicate → split → write → report` 的确定性闭环。

### Day 6：数据契约与 Manifest（4–5h）

- 定义输入记录、规范化记录、拒绝记录和输出 shard 的 Schema；
- Manifest 至少记录来源、许可证状态、下载时间、原始哈希、处理配置哈希、记录数和字节数；
- 原始数据、缓存和生成 Artifact 默认不提交 Git。

### Day 7：Reader 与规范化（4–6h）

- 首月只支持一种正式输入格式；测试夹具可用小型 `jsonl`/文本；
- 实现编码检查、Unicode 规范化、换行与空白策略；
- 明确空文档、损坏记录、超长行和非文本内容的行为。

### Day 8：Filter 与去重（4–6h）

- 实现可解释的长度/质量过滤，拒绝原因必须计数；
- 先做精确哈希去重，近似去重列为 P1；
- 测试处理顺序、重复输入和多次运行确定性。

### Day 9：确定性切分与 Writer（4–5h）

- 用内容哈希进行 train/validation/test 切分，禁止先后顺序造成漂移；
- Writer 输出稳定排序、固定编码和 manifest；
- 测试不同输入顺序下切分结果相同。

### Day 10：流水线 Smoke 与报告（4–6h）

- 在仓库内极小、可公开的测试夹具上运行完整流水线；
- 输出输入/保留/拒绝/重复数量、字符与字节统计、拒绝原因分布；
- 新建实验记录，保留精确命令、环境、结果和失败。

**周验收：** 完整流水线在 CPU 上数分钟内完成；二次运行输出哈希一致；所有拒绝可归因。  
**注意：** 本周夹具通过不代表正式数据获批。

## 第 3 周：正式数据审计与 Data Card

**目标：** 只批准一个正式数据源，并把“可用”与“适合”分开证明。

### Day 11：候选数据源决策（3–5h）

- 最多比较 3 个候选源：来源稳定性、许可证、语言/领域、规模、下载成本、脏数据风险；
- 许可证不清晰、来源不可追踪或需要规避访问限制的数据直接淘汰；
- 写 ADR，确定一个正式源和一个不采用的备选源。

### Day 12：获取与原始审计（4–6h）

- 使用可恢复、带校验的数据获取方式；
- 保存原始文件哈希、版本标识和抽样记录；
- 扫描空文档、重复、编码异常、潜在 PII/Secret 和许可证风险。

### Day 13：规则校准（4–6h）

- 在固定小样本上人工检查保留/拒绝结果；
- 每次只调整一种过滤规则，记录前后变化；
- 保存被拒绝样本的脱敏摘要，不提交不允许再分发的原文。

### Day 14：冻结 v1 数据集（4–6h）

- 运行正式小规模数据流水线；
- 生成冻结 manifest、切分哈希与统计报告；
- 验证训练、验证、测试之间无精确重复。

### Day 15：Data Card 与复现审计（4–5h）

- 完成来源、许可证、用途、处理、统计、风险、局限和删除/修正策略；
- 从原始数据重新生成一次，比较 manifest 与输出哈希；
- 记录未解决风险，不能把“未发现”写成“不存在”。

**周验收：** 数据 v1 可追踪、可重建、可解释；Data Card 中无“待填写”的关键项。  
**停止条件：** 正式源许可证或来源不能确认时，不进入正式 Tokenizer 训练；改用经审计的极小公开/自有语料完成接口验证，并保留阻塞记录。

## 第 4 周：最小 BPE、正式 Tokenizer 与 G1

**目标：** 同时证明原理理解和工程可用性。

### Day 16：BPE 规格先行（3–5h）

- 写明输入单位（byte/character）、预分词、特殊 Token、Tie-break 和停止规则；
- 准备可手算的小语料与期望 merge 序列；
- 先写测试，再实现训练过程。

### Day 17：手写最小 BPE（5–7h）

- 实现词频初始化、pair 统计、确定性合并、词表/merge 保存与加载；
- 不追求大规模性能，不用第三方 Tokenizer 替代核心逻辑；
- 对照手算案例逐步验证。

### Day 18：编码、解码与边界测试（4–6h）

- 实现 encode/decode 及特殊 Token 策略；
- 覆盖空串、Unicode、中英文、空白、重复字符、未知字节和损坏模型文件；
- 属性测试：合法文本在既定规范化策略下可 round-trip。

### Day 19：工程版 Tokenizer 与评测（5–7h）

- 使用成熟 Tokenizer 库训练工程版，保存版本、配置和哈希；
- 固定训练/验证切分，比较字符/byte 基线、手写 BPE 与工程版；
- 报告词表规模、fertility、压缩率、未知率、速度和特殊 Token 正确率；
- 不将不同预分词或不同数据的结果直接归因于 BPE 算法。

### Day 20：G1 审计与发布（4–6h）

- 在新环境复现数据 → Tokenizer → 评测；
- 检查测试、配置快照、manifest、哈希、实验记录和 Data Card；
- 更新 README、进度台账和已知限制；
- 形成 `v0.2-data-tokenizer` 候选，并写下第 2 月 Transformer 输入契约。

**门禁 G1：**

- 手写 BPE 与工程版 Tokenizer 均有独立测试；
- 固定输入和配置重复运行得到一致词表/merge 哈希；
- 验证集 round-trip 与特殊 Token 测试全部通过；
- 评测报告包含基线、分母、硬件/环境、Run ID 和失败记录；
- Data Card、Tokenizer 配置和冻结 Artifact 可以互相追踪。

## 4. 每周时间分配

| 工作类型 | 60h/周基线 | 说明 |
|---|---:|---|
| 实现与调试 | 32h | 以当周 P0 为主，不跨门禁堆功能 |
| 测试、评测、失败分析 | 10h | 先正确性，再性能 |
| 原理与官方文档/源码学习 | 8h | 只读当前阶段直接需要的内容 |
| README、实验记录与陌生环境复现 | 6h | 与代码同时完成 |
| 缓冲或 P1 | 4h | P0 延误时自动回收 |

每天建议保留两个 3 小时深度工作块、一个 2 小时测试/阅读块和一个 1–2 小时记录/复盘块。若核心任务提前完成，先补测试和复现，再做 P1；只有 G1 提前通过时，才允许在第 4 周编写 Transformer 输入契约和测试规格，不提前启动长训练。

## 5. 本月 P0 / P1 切分

### P0 必做

- 可安装包、统一 CLI、lint/typecheck/test/smoke；
- 配置、日志、Run ID、环境与 Git 快照；
- 单格式数据流水线、精确去重、确定性切分、统计；
- 一个正式数据源的审计、manifest 与 Data Card；
- 手写最小 BPE、工程版 Tokenizer、固定评测和文档；
- Windows 本机或 Linux 环境至少一种完全复现，CI 通过。

### P1 有余力再做

- Docker CPU 开发镜像；
- 多格式 Reader、并行数据处理、近似去重；
- Tokenizer 训练性能优化或多词表规模消融；
- Windows 与 Linux 双平台 CI；
- 更完整的 PII 扫描和 SBOM。

P1 不能成为 G0/G1 的阻塞条件。

## 6. 我们后续按进度共同构建的方式

每次推进以一个可验证小批次为单位，不一次跨越多个门禁：

1. 你告诉我本周可投入时间、当前设备和希望推进的 Day/任务；
2. 我先检查仓库、资源卡、当前测试和进度台账；
3. 我只实现当前批次代码与测试，运行验证，并记录精确结果；
4. 我更新 `docs/month_01_progress.md`、实验记录和必要文档；
5. 只有当前退出条件满足后，才把下一项标为进行中；
6. 若失败，保留失败记录，先定位根因，再决定修复、降级或停止。

建议单次协作粒度为半天到两天，例如“完成 Day 2 包与依赖基线”，而不是“直接完成第一个月”。
